# Forge 1.20.1 详细重构计划

## 目标与边界

在保留现有功能、卡片 NBT、API v1 和 Forge 1.20.1 / Java 17 支持的前提下，降低扩展模组升级风险，使编码、上传和拉料可以独立测试。
这是一份分阶段计划，不代表本轮已经完成全部重构；本轮的实际修复与验证另见依赖审计记录。

- 不把 Forge 分支机械改成 NeoForge 1.21 数据组件或 payload API。
- 不引入与现有 `ModCapabilities`、`EncodeBatchPolicy`、`ModCommonSetup`、`MachineTransferProfile` 重复的框架。
- 不在同次提交混入大规模格式化、命名调整和行为变化。
- 每个阶段至少拆成“特征测试 → 最小提取/修复 → 集成验收”；每个独立完成项单独本地提交。
- 工时按阶段实施时重新评估，优先级和验收结果比未经验证的日期承诺重要。

## 当前结构与主要风险

1. `EncodePatternService` 同时处理包请求、网络/终端上下文、材料选择、样板编码、重复检查、空白样板消耗和多种上传路径，是最高风险的业务集中点。
2. `SequentialUploadQueue` 与 `InventoryPatternUploadQueue` 用静态队列、多个标志和计数维护客户端会话，迟到回执、取消和重开操作容易互相污染。
3. `EaepDirectCompat`、`EaepReflection` 与上传 Mixin 横跨本模组和 EAEP 自身入口；仅保护自有包而不保护原生上传/取消入口，不能保证物品守恒。
4. `MachineTransferProfiles` 原有 JEI 类型静态初始化把客户端依赖带入服务器；可选依赖必须从公共入口的类加载层面隔离。
5. `EncodePatternButtonController`、`JeiPatternSubstitutionUi` 和 `RecipeFinderScreen` 混合渲染、查询、缓存与状态，不能只靠拆小文件改善职责。
6. `ModNetworking` 已有方向限制和大小校验，`network/codec` 已有 Forge 适配，不应再引入第二套协议框架。
7. `NbtTear*` 与多个合成 CPU/供应器 Mixin 已形成专用模块，后续重点应是嵌套上下文、异常清理和守恒测试，而非重新集中回单一工具类。
8. 已有 JUnit 与主菜单延迟 Mixin 冒烟；主菜单不能证明真实网络权限、世界交互和服务端可选依赖安全。

## P0：建立可重现基线与安全边界

### P0.1 依赖与启动矩阵

- 固定开发测试依赖，记录上游版本 ID、Java/Mixin 要求、必需前置和回退原因。
- 保留 Modrinth 特定加载器版本 ID，避免同一版本字符串解析到 Fabric 包。
- 将纯开发依赖调整与面向用户的更新说明分离。
- 验收：Java 17 完整构建、实际重跑单元测试、完整运行依赖主菜单冒烟、发布 JAR 元数据与资源检查。
- 提交示例：`优化：统一依赖兼容基线`；纯依赖变更不新增用户 changelog。

### P0.2 背包样板上传授权与守恒

- 服务端将预选请求与玩家、槽位、完整物品/NBT 身份和有效授权绑定。
- 同时覆盖本模组上传包、EAEP 原生上传/取消入口、清理 pending、断线与重启后的失效状态。
- 区分 `SUCCESS`、`DUPLICATE`、`FAILED`；复制出的 pending 不能作为真实已托管物品退回，真正消耗只发生一次。
- 验收：预选后换槽/换 NBT、重放、直接原生上传、直接原生取消、重复样板、失败重试、断线重连均不复制、不丢失物品。
- 提交示例：`修复：绑定背包样板上传授权`；中英文 changelog 仅概括玩家可见问题。

### P0.3 可选依赖隔离

- 服务端机器 ID、菜单、槽位布局与客户端 JEI 配方类型/注册分离。
- 排查公共 API、网络注册、事件订阅、静态字段和方法签名中的客户端/可选类引用。
- 统一有模组才加载适配器；Mixin 插件不能提前加载目标类。
- 验收：无 JEI 的隔离类加载测试；后续补最小 AE2-only 专用服务端进入世界测试，JEI-only/EMI-only 客户端都能启动。
- 提交示例：`修复：隔离服务端机器拉料依赖`。

## P1：拆分编码业务，明确事务边界

### P1.1 固化输入与预览一致性

- 以现有 `EncodePatternPacket`、`EncodeBatchPolicy` 和 `PatternEncodingPreview` 为边界补特征测试。
- 覆盖物品/流体/四类 Mekanism 化学品、书签优先、多候选、自循环过滤、概率副产物、过大包拒绝。
- 验收：相同规则快照下预览与最终编码一致，错误输入不消耗空白样板。

### P1.2 提取纯计算计划

- 从 `EncodePatternService` 提取不访问玩家/世界的编码计划计算，使用不可变输入和显式结果/失败原因。
- 终端与无线网络解析继续复用现有 resolver；将请求校验、上下文解析、计划计算、提交执行分层。
- 避免为每个小方法创建接口，只有真实跨平台/第三方边界才使用适配接口。
- 验收：纯计划测试不启动 Minecraft；服务端仍重新验证客户端建议，不能信任客户端预览结果。

### P1.3 消耗与提交

- 将空白样板预留、编码、上传、失败恢复作为可审查的单次事务；明确每种返回值是否已经消费/插入。
- 将供应器、矩阵、Neo ECO 上传结果统一为领域结果，再由适配器解释第三方 API。
- 验收：断网、供应器满、重复、权限不足、输出失败与异常分支中物品总量守恒，批量部分成功有明确回执。
- 每个提取单独提交；不改变行为的重构不写用户 changelog。

## P2：顺序上传状态机与会话协议

1. 先补 `SequentialUploadQueue` / `InventoryPatternUploadQueue` 的超时、取消、重试、重开和乱序回执测试。
2. 提取纯状态机：`IDLE → PREPARING → WAITING_SELECTION → UPLOADING → COMPLETED/CANCELLED/FAILED`，用状态值替换相互矛盾的 Boolean 组合。
3. 请求/回执携带服务端认可的会话 ID 与步骤序号，拒绝旧会话、重复与乱序回执；明确重试是否幂等。
4. 网络协议变更需独立升版，客户端与服务端同时升级；不能悄悄改变现有协议 4 的字段布局。
5. 统一手动取消、stopuploads、关界面、断线、维度切换和服务端停止的生命周期清理。
6. 验收：模拟高延迟、丢包/重复回执、旧会话 final 到达新会话时，不错误结束、不重复消费、不永久锁住队列。
7. 提交拆分：状态机测试、客户端提取、协议升版、服务端幂等处理各一项；用户条目只写实际体验改进。

## P3：扩展模组兼容层与 Mixin 收敛

- 盘点 `compat/**`、`integration/**`、Mixin 的目标版本、注入方法描述符、必需/可选级别。
- 将 EAEP/Neo ECO/AdvancedAE/AE2LT/AE2CS 的直接调用集中在各自适配器，公共业务仅依赖领域结果。
- 对反射入口缓存解析结果、区分“未安装”“版本不支持”“执行失败”，避免吞掉所有异常后伪装成功。
- 为每个适配器建立已验证版本矩阵；不使用无限开放版本范围暗示所有未来版本都支持。
- 扩充延迟 Mixin 冒烟到全部实际目标，配合最小依赖/单个扩展/完整扩展测试组合。
- 验收：移除任一可选模组后可启动，版本变化时有清晰日志，不因反射失败丢失物品。

## P4：客户端状态、索引与缓存

### P4.1 编码按钮与替换 UI

- 从 `EncodePatternButtonController` 提取查询状态/动作分派，渲染只消费已计算的只读状态。
- `JeiPatternSubstitutionUi` 独立管理候选选择和持久化规则，JEI/EMI 共享规则而非共享界面对象。
- 验收：同一配方每 tick 不重复发包，候选/书签/终端变化正确失效，JEI 与 EMI 行为一致。

### P4.2 查询器索引与筛选

- 保留现有 `RecipeFinderClientState`、`RecipeFinderScreenState`、格式化辅助类，进一步分开索引、筛选计划、分页和批量执行。
- 建立配方重载、切换世界、改变服务器规则时的索引世代号，旧查询结果不得覆盖新会话。
- 验收：大配方库下索引工作可取消，不长时间阻塞渲染线程，筛选/选择结果稳定。

### P4.3 缓存生命周期

- 为 craftable、preview、machine recipe 与 JEI 书签缓存明确键、容量/过期条件和世界/玩家作用域。
- 将断线/重载清理挂到统一生命周期入口，但不把所有缓存重新合成全局可变单例。
- 验收：换服不显示旧网络状态；不因失效风暴每帧发包；有真实大配方场景的测量数据再做性能承诺。

## P5：功能卡、公共 API 与资源质量

- NBT 撕裂上下文采用成对进入/退出，所有异常路径清理 ThreadLocal；测试嵌套模拟、真实执行与回滚互不污染。
- 红石卡覆盖边沿/电平、重载配置与断线，保持旧 NBT 键和默认行为。
- API v1 使用独立契约测试，记录 null/空列表/线程要求；破坏性变更另开 API 版本，不改变现有接口语义。
- 中英文翻译键、配方、模型、声音和 GUI 资源加入自动校验，防止只编译通过但游戏缺资源。
- 验收：旧存档样板/卡片可继续使用，第三方最小消费者可编译加载，中英文键一致。

## 统一完成标准

- 每项记录具体变更、关联风险、自动测试、人工复现步骤和未覆盖场景。
- Java 17 `gradlew.bat build` 与相关测试通过；关键测试不能仅以 `UP-TO-DATE` 作为本次重跑证据。
- Mixin/依赖变更补主菜单冒烟；服务端逻辑补最小服务端测试；物品操作补世界内守恒验证。
- 更新用户可见 changelog（若适用），检查本地分支、暂存差异和作者身份，短标题本地提交，不推送。
- 某项无法完成时保留具体失败日志和待办，不把计划、静态检查或主菜单通过当成世界内验收。
